# SameCall · 同样调用，同样回执

旧版包裹分发台用 `dispatch(lane, request, parcel)` 投递包裹。新版把真正的投递接口改成了 `dispatch_v2(contents, /, label="plain", *, order_id, chute, preview=False)`：包裹内容放在第一位，订单号和通道按新名字传入，新增的标签和预览开关沿用新版默认值。SameCall 让它们分别处理两笔虚构订单，用实际写入的投递记录选出替代方法，而不是相信方法名或返回的数字。

## 跑一次自动适配

在仓库根目录执行（Python 3.9+，只用标准库，无需账号或网络）：

```sh
python3 demo.py                       # 发现候选、试投、打包并复验
python3 -I build/parcel-adapter.pyz   # 单独运行打好的成品
```

第二条命令会输出：

```json
{"method": "dispatch_v2", "receipts": [1, 2], "delivery_count": 2, "retry_receipt": 1}
```

## 用旧接口提交自己的示例订单

成品仍提供 `dispatch(lane, request, parcel)`。调用方不需要知道新版方法叫 `dispatch_v2`。用同一个数据库运行下面的命令：

```sh
python3 -I build/parcel-adapter.pyz dispatch --db build/orders.sqlite blue order-7 lantern
python3 -I build/parcel-adapter.pyz dispatch --db build/orders.sqlite blue order-7 lantern
```

在新数据库里，两次都返回 `{"receipt": 1}`，只投递一次。把第二条命令的 `lantern` 改成 `clock` 再试：同一订单号不能改投别的包裹，命令以非零状态退出，原记录保留。这里的数据库会保留在指定路径；不带参数的复验仍使用临时数据库。

## 怎么找到方法和参数的对应关系？

[构建器](demo.py)先对旧版跑一次投递，取得回执基线，再枚举新版类自身定义的、名字以 `dispatch` 开头的实例方法。[映射器](call_plan.py)读取每个候选的签名，把旧入口的三个值一一分配给新参数，先选满三个目标参数（必须包含全部必填项），每组选出的参数试 **6 种排列**。每种排列都用全新的临时数据库，从旧入口执行同一组试投。参数名不参与评分；方法名没改、只有参数变化时也用同一套规则。

本例唯一通过的调用方式是：

```python
# 调用方仍写 desk.dispatch(lane, request, parcel)
target.dispatch_v2(parcel, order_id=request, chute=lane)
```

其中 `contents` 是仅限位置参数，因此直接传 `parcel`；`chute` 是仅限关键字参数，因此传 `chute=lane`。新增的 `label` 和 `preview` 不传，因此仍按普通标签实际投递。如果必须跨过一个可选的仅限位置参数才能传后面的值，适配器使用该位置在目标方法上声明的默认对象，不把它复制进绑定规则。构建输出的 `binding` 会显示这份映射；成品保存它，不会在每次投递时重新猜。

| 新版候选 | 实际行为 | 结果 |
| --- | --- | --- |
| `dispatch_preview` | 总是返回 `1`，却不写投递记录 | 淘汰：只有编号，没有投递 |
| `dispatch_redirect` | 写入记录，也返回真实编号，但把包裹投到 `other-lane` | 淘汰：回执对应的通道不对 |
| `dispatch_v2` | 把包裹投到指定通道，重试时返回原回执 | 通过 |

只有**恰好一个“方法 + 参数映射”组合**通过，才会打包。即使只有一个候选方法，只要它有两种排列都通过，也视为歧义，不替换旧包。旧入口仍提供三个值；如果新版必填项不足三个，也会尝试将旧值映射到可选项。两组选中的参数都能复现回执时同样停止，不按名字猜。不转换数据类型，也不尝试可变参数。

## 一张回执怎么证明包裹投对了？

[验证程序](check_route.py)按 **A → B → A** 提交订单：A 把纸风筝投到蓝色通道，B 把锡鸟投到金色通道，最后原样重试 A。每次提交都会关闭并重新打开分发台，但三次共用该候选的数据库，避免把进程内的记忆误当作重试保证。

验证程序随后用**独立的 SQLite 连接**读取投递表，将返回的回执号与库里的订单号、通道、包裹内容逐项对照。A 和 B 必须有不同回执，第二次提交 A 必须拿回第一次的回执，而且表中只能有两条记录。这就是输出里“提交三次、投递两次、重试回执仍为 1”的含义。

验证程序还会用 A 的订单号提交不同包裹：必须被拒绝，拒绝后投递表也必须保持不变。

选定方法后，构建器把兼容入口、绑定规则、自建新版服务、验证程序和许可证装进 `.pyz`，再用独立 Python 进程和全新数据库通过成品的旧入口 `dispatch` 重跑同一组检查。成品报告的方法必须是选中的方法，回执结果必须与旧版基线一致，才会原子替换本地适配包；复验失败则保留之前的版本。

运行 `python3 -m unittest -v` 可检查候选淘汰、无唯一解时停止，以及成品复验失败时保留旧包。
