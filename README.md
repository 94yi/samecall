# SameCall · 同样调用，同样回执

旧版包裹分发台用 `dispatch(lane, request, parcel)` 投递包裹。新版把真正的投递接口改成了 `dispatch_v2(contents, /, label="plain", *, order_id, chute, preview=False)`：包裹内容放在第一位，订单号和通道按新名字传入，新增的标签和预览开关沿用新版默认值。SameCall 让它们分别处理两笔虚构订单，用实际写入的投递记录选出替代方法，而不是相信方法名或返回的数字。

## 跑一次自动适配

在仓库根目录执行（Python 3.9+，只用标准库，无需账号或网络）：

```sh
python3 demo.py                       # 发现候选、试投、打包并复验
python3 -I build/parcel-adapter.pyz   # 单独运行打好的成品
```

第二条命令会输出：

```json
{"method": "dispatch_v2", "receipts": [1, 2], "delivery_count": 2, "retry_receipt": 1}
```

## 用旧接口提交自己的示例订单

成品仍提供 `dispatch(lane, request, parcel)`。调用方不需要知道新版方法叫 `dispatch_v2`。用同一个数据库运行下面的命令：

```sh
python3 -I build/parcel-adapter.pyz dispatch --db build/orders.sqlite blue order-7 lantern
python3 -I build/parcel-adapter.pyz dispatch --db build/orders.sqlite blue order-7 lantern
```

在新数据库里，两次都返回 `{"receipt": 1}`，只投递一次。把第二条命令的 `lantern` 改成 `clock` 再试：同一订单号不能改投别的包裹，命令以非零状态退出，原记录保留。这里的数据库会保留在指定路径；不带参数的复验仍使用临时数据库。

## 怎么找到方法和参数的对应关系？

[构建器](demo.py)先取得旧版回执基线，再检查新版类自身定义的 `dispatch*` 实例方法。默认直接从[新旧接口定义](service.py)提取目录，不需要另写 JSON。运行 `python3 demo.py --catalog` 可以查看提取结果，不会试投或打包。方法名、参数名、位置限制和默认值来自 Python 签名；字段身份和改名关系只读签名上明确提供的元数据。例如：

```python
Contents = Annotated[str, FieldID("desk.contents")]
# 旧版的 parcel 和新版的 contents 都使用 Contents，因此可确定是同一字段。
# 新版的 order_id 则声明为 Annotated[str, RenamedFrom("request")]。
```

只有标记本身需要在接口定义中声明一次，不用在外部目录重复登记。当前读取运行时的 `Annotated`，不会求值字符串注解。没有声明的字段不会因为同名、同为字符串或位置相近就被认定相同。提取结果的含义是：

- `legacy_ids` 给每个旧字段一个稳定标识。目标参数的 `ids` 若与旧标识相同，就固定对应关系；若新旧标识不同就排除该配对。旧字段没有标识时，不能据此排除它。
- `renamed_from` 是明确的改名声明，例如 `"order_id": "request"`。它与标识冲突、引用不存在的参数，或两个参数争用同一旧字段时，构建停止。
- 没有声明的字段仍是未知项，不按名字猜。映射必须覆盖目标方法的全部必填项，其他位置才尝试剩余旧值的排列。

运行 `python3 demo.py --compare` 可在同一套自建候选上分别试投，不替换适配包。每次试投指**用一种映射跑完整回执检查或检查至失败**，不含旧版基线和成品复验：

| 模式 | 预览方法 | 错投方法 | 真正的投递方法 | 合计 |
| --- | ---: | ---: | ---: | ---: |
| 只看签名 | 6 | 6 | 6 | 18 |
| 从接口定义提取声明 | 2 | 2 | 1 | 5 |
| 再看源码和调用样例 | 2 | 0 | 1 | 3 |

试投上限默认是整个搜索共 64 次，可用 `python3 demo.py --max-trials 5` 调整。恰好在第 5 次排完且唯一通过，可以进入成品复验；用完仍有候选未试，即使已找到一个成功映射也停止，旧包不变。每一种剩余映射都用独立的临时数据库试投；一旦确认第二种也通过，就停止。

本例唯一通过的调用方式是：

```python
# 调用方仍写 desk.dispatch(lane, request, parcel)
target.dispatch_v2(parcel, order_id=request, chute=lane)
```

其中 `contents` 是仅限位置参数，因此直接传 `parcel`；`chute` 是仅限关键字参数，因此传 `chute=lane`。新增的 `label` 和 `preview` 不传，因此仍按普通标签实际投递。如果必须跨过一个可选的仅限位置参数才能传后面的值，适配器使用该位置在目标方法上声明的默认对象，不把它复制进绑定规则。构建输出的 `binding` 会显示这份映射；成品保存它，不会在每次投递时重新猜。

| 新版候选 | 实际行为 | 结果 |
| --- | --- | --- |
| `dispatch_preview` | 总是返回 `1`，却不写投递记录 | 淘汰：只有编号，没有投递 |
| `dispatch_redirect` | 写入记录，也返回真实编号，但把包裹投到 `other-lane` | 淘汰：回执对应的通道不对 |
| `dispatch_v2` | 把包裹投到指定通道，重试时返回原回执 | 通过 |

只有**恰好一个“方法 + 参数映射”组合**通过，才会打包。即使只有一个候选方法，只要它有两种排列都通过，也视为歧义，不替换旧包。旧入口仍提供三个值；如果新版必填项不足三个，也会尝试将旧值映射到可选项。两组选中的参数都能复现回执时同样停止，不按名字猜。不转换数据类型，也不尝试可变参数。

## 两个版本都没有字段标记时怎么办？

`python3 demo.py --plain --compare` 比较另一对自建版本，两边都没有字段标识和改名声明。新版用 `x, y, z` 命名，所以名字也帮不上忙。

[源码筛选器](source_evidence.py)可以跟踪局部变量赋值、一次普通实例辅助方法调用，以及按样例值能确定方向的简单条件分支。它把[调用样例](examples.py)代入，计算各映射**将要登记**的通道、订单号和包裹，不写数据库。如果对同一笔输入，新旧版本会登记不同内容，这种映射就不必试投。登记内容相同只代表值得试投，不代表已拿到回执。

| 无标记示例使用的证据 | 实际试投次数 |
| --- | ---: |
| 只看签名（或再看空目录） | 18 |
| 仅识别直接转发，同时给两版样例 | 18 |
| 扩展源码分析 + 旧版调用样例 | 8 |
| 再加新版调用样例 | 7 |

新版方法先判断是否预览，再把包裹赋给局部变量，最后由辅助方法把通道、订单号、包裹传给登记函数。两个投递样例都走实际投递分支；不会把这条路径当成预览分支的行为。

旧样例里通道和订单号碰巧都是 `blue`，换位也看不出差别。新版样例的两个值不同，再比较一次才能排除换位。最终 7 次中，1 次验证真正的投递方法；其余 6 次验证只返回编号、不提供投递记录的预览方法。错投方法固定投向另一通道，已被样例排除。

支持的条件是普通标量的真假、相等或不等；只读取该样例实际经过的分支。看不到源码、路径上有循环、超过一层辅助调用或无法解释的表达式时，该样例不作判断。没有其他反例就继续真实试投，不按首个成功映射换包。运行 `python3 demo.py --plain --max-trials 7` 可打包并复验这个无标记示例，产物在 `build/plain/parcel-adapter.pyz`，与默认示例分开。

## 一张回执怎么证明包裹投对了？

[验证程序](check_route.py)按 **A → B → A** 提交订单：A 把纸风筝投到蓝色通道，B 把锡鸟投到金色通道，最后原样重试 A。每次提交都会关闭并重新打开分发台，但三次共用该候选的数据库，避免把进程内的记忆误当作重试保证。

验证程序随后用**独立的 SQLite 连接**读取投递表，将返回的回执号与库里的订单号、通道、包裹内容逐项对照。A 和 B 必须有不同回执，第二次提交 A 必须拿回第一次的回执，而且表中只能有两条记录。这就是输出里“提交三次、投递两次、重试回执仍为 1”的含义。

验证程序还会用 A 的订单号提交不同包裹：必须被拒绝，拒绝后投递表也必须保持不变。

选定方法后，构建器把兼容入口、绑定规则、自建新版服务、验证程序和许可证装进 `.pyz`，再用独立 Python 进程和全新数据库通过成品的旧入口 `dispatch` 重跑同一组检查。成品报告的方法必须是选中的方法，回执结果必须与旧版基线一致，才会原子替换本地适配包；复验失败则保留之前的版本。

运行 `python3 -m unittest -v` 可检查候选淘汰、无唯一解时停止，以及成品复验失败时保留旧包。
